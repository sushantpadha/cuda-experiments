# Review of 2A and 2B findings

2026-10-04. Independent re-check of `2A-compute-sharing/FINDINGS.md` and `2B-eviction-metrics/FINDINGS.md`. I re-ran every key command on the same machine (RTX 4050 Laptop, driver 580.178.04, CUDA 13.0), read the probe code, and checked the cited sources. The MPS runs used the user-local daemon (`/tmp/claude-1000/mpsp`), and the server log shows 24 new client connections during my MPS runs. Each measurement was run 1 to 3 times, so the numbers below are still preliminary.

Verdicts: **CONFIRMED** (reproduced, or the source says so), **WEAK** (roughly right but overstated, unreproducible from the README, or confounded), **WRONG** (contradicted by my runs or by the source).

## 2A: compute sharing

| Claim | Verdict | Reason and my numbers |
|---|---|---|
| No MPS: two processes time-slice | CONFIRMED | 4 blocks alone: 451 and 444 ms; two at once: 915 and 914 ms, with `%globaltimer` intervals overlapping within 2 ms. I added the missing control: 8 blocks in one process take 444 ms, so the doubling cannot come from lack of SMs. The kernel is valid: it is a dependent FMA chain whose result is stored, so it cannot be optimised away. `%globaltimer` is device-wide and reads as Unix-epoch ns, within about 50 ms of host `CLOCK_REALTIME`, so it can be compared across processes. |
| MPS: kernels run concurrently | CONFIRMED | 2 and 3 clients each took 443 ms, against 454 ms alone. |
| Green contexts in one process are disjoint and concurrent | CONFIRMED | Same SM sets as reported; 642 ms each, against 627 ms for one alone. |
| Two processes with disjoint green contexts, no MPS, still time-slice | CONFIRMED | 1298 ms each, against 627 and 628 ms alone. |
| "Green contexts partition SMs only inside one process" | WRONG (framing) | It holds only without MPS. With MPS, two clients on disjoint green groups (+10/-10) each took 638 ms, while two clients on the same group (+10/+10) took 660 and 1188 ms. So green contexts plus MPS do give isolated SM partitions across processes, which is the useful result for libvmem and is missing from the Answer. The guide quote is taken from a passage contrasting MPS *static partitioning* with green contexts. Its "applicable within a single process **too**" does not say "only". |
| VMM works under MPS (device and `HOST_NUMA`, remap, fd export/import) | CONFIRMED | `vmm`, `share` and `remapbusy` all passed with 0 bad words under MPS, with numbers equal to the no-MPS runs. "The MPS docs list no VMM restriction" could not be checked offline. |
| `PINNED_DEVICE_MEM_LIMIT=128M` makes a 256 MiB `cuMemCreate` fail | CONFIRMED | `spatial.cu:196 cuMemCreate -> CUDA_ERROR_OUT_OF_MEMORY`; with 1G it passes. |
| `ACTIVE_THREAD_PERCENTAGE=25` gives 4 SMs, 1503 ms | CONFIRMED (with my control) | 1498 ms. The original evidence was `%smid`, which the same file calls unreliable under MPS. A 4-SM green context gives 1494 ms for the same kernel, which supports 4 SMs (25% of 20 is 5; the driver probably rounds down to whole TPCs of 2 SMs, which is my inference). |
| MPS: one client's fault kills the other | CONFIRMED | B failed with `cudaErrorIllegalAddress` at `cudaStreamSynchronize`. The server log says "devices will be reset: 0", sets a sticky error on both PIDs, then runs "Destroy server context" and "Creating server context". So the server process survives, but its device context is rebuilt. A new client ran normally afterwards (445 ms). I did not test whether an idle client with no work in flight also dies. The quoted MPS-docs sentence could not be checked offline. |
| No MPS: B survives A's fault | CONFIRMED | I added host timestamps. B's kernel ran from about 626.41 s to 629.21 s and A's fault ran from 627.39 s to 627.56 s, so the two overlapped. B finished normally in 2855 ms. The original command did not prove the overlap. |
| Xid 31 logged, no reboot | CONFIRMED | `Xid 31 ... FAULT_PDE ACCESS_TYPE_VIRT_READ`. |
| Bandwidth: device 187 GB/s, `HOST_NUMA` 13.4 GB/s, random reads 1860 / 128 M/s | CONFIRMED | 187.3 to 187.5, 13.4, and 1860 to 1870 / 126 to 128.5. The read kernels keep their loads live, because the result is conditionally stored. The host numbers come from a `CU_MEM_LOCATION_TYPE_HOST_NUMA` handle, and 13.4 GB/s matches the Gen4 x8 link. Note that 187 GB/s is 97% of the 192 GB/s theoretical peak, which is unusually high and not checked with `ncu`. |
| Remap copy 20 ms, unmap/release/map/access 2.7 ms | CONFIRMED | 20.7 ms (13.0 GB/s), 2.71 to 2.72 ms. |
| Two processes remapping at once: 5.2 GB/s copy, 8.4 to 8.9 GB/s reads | WEAK | No command is given, and the numbers depend on how the two runs line up. Two concurrent `./spatial vmm` gave 6.6/6.6 GB/s copy and 6.4/6.5 GB/s reads without MPS, and 6.6/6.6 and 6.7/6.8 with MPS. Without MPS the halving is partly time slicing, not PCIe sharing alone, so the "(shared PCIe)" label is only shown for the MPS case. |
| VRAM per bare context: 87 / 80 MiB | WEAK | The two numbers use different metrics. Without MPS, device-used rose by 87 MiB while `nvidia-smi` attributed 82 MiB to the process. With MPS, each client is 80 MiB, plus about 30 MiB for the server, which is not counted. The context runs no runtime modules, so real applications will use more. The `hold` run is not in the README. |
| Granularity 2 MiB for both | CONFIRMED | |
| Remap does not wait for an unrelated kernel | CONFIRMED | BUSY: create 8.8 ms, copy 5.3 ms, unmap 0.04 ms, map 1.5 ms, `kernel_done_before_end=0`, kernel wall 443 ms. The wall time equals the bare kernel time, so the kernel started immediately and ran during the remap. Same result under MPS. The test is single-process only; cross-process remap under MPS was not tested. |
| Nixie syncs the whole context (`schedule/mod.rs`) | WEAK | `cuCtxSynchronize` is at `schedule/mod.rs:116`, but only on the scheduler `Disable` path, which pauses the whole process. It is not presented as a requirement of remapping, so "per-buffer remap needs no sync, unlike Nixie" compares two different operations. |
| Remap under a reading kernel crashes | CONFIRMED | 3 of 3 runs, `cudaErrorIllegalAddress`, Xid 31 `FAULT_PDE`. |
| `cuMemMap` refuses an already-mapped range | CONFIRMED (not by their code) | Tagged [run], but `spatial.cu` has no such test. My scratch test returned `CUDA_ERROR_INVALID_VALUE`. |
| `%smid` is virtualised under MPS | CONFIRMED (with my control) | Both disjoint-green clients report 0..9 at 638 ms each. Clients on the same group slow down (1188 ms), so the disjoint ones really are separate. Plain MPS clients also both report {0,2,4,6}, which could also be true co-residency. |
| Nixie has no MPS or green-context code | CONFIRMED | The only matches for "green" are terminal colours and the only "mps" match is `tokio::mpsc`. |

## 2B: eviction signals

| Claim | Verdict | Reason and my numbers |
|---|---|---|
| Argument-scan ground truth table (direct, struct, interior, indirect) | CONFIRMED | Both shims gave {0,1}, {2,3}, {4} and {0}. |
| `LD_PRELOAD` misses cuBLAS; CUPTI sees it, plus a workspace | CONFIRMED | `cuLaunchKernel calls seen=0`; CUPTI shows `ampere_sgemm_128x64_nn allocs={0 1 2 7}` and 1005 launches. |
| "`LD_PRELOAD` cannot see library launches" | WEAK | It is true only for this shim, which interposes exported symbols. `libcublas.so.13` has no undefined cudart symbols, because it links cudart statically and resolves driver calls through entry points. An `LD_PRELOAD` that interposes `cuGetProcAddress` or `dlsym`, as HAMi-core does, can see these launches. |
| CUDA 13 stubs call `__cudaLaunchKernel` | CONFIRMED | `crt/host_runtime.h:140` calls `__cudaLaunchKernel_helper` (`crt/device_functions.h:2951`), which calls `__cudaLaunchKernel` (`:2932`). `nm -D argapp` shows only `__cudaLaunchKernel@libcudart.so.13`. The "[run]" part, that a shim with only `cudaLaunchKernel` sees zero launches, cannot be reproduced: the current `argshim` hooks both symbols and keeps no per-symbol count. A missing caveat: nvcc's default is `-cudart static`, and with static cudart no `LD_PRELOAD` runtime hook works on any CUDA version. |
| Nixie hooks only `cudaLaunchKernel` | WRONG (detail) | `intercept_launch.rs:26,51` hooks `cudaLaunchKernel` **and** `cudaGraphLaunch`, plus stream-capture and instantiate hooks. The conclusion that Nixie misses `<<<>>>` launches from CUDA 13 binaries still follows, since it does not hook `__cudaLaunchKernel`. It remains [inferred]. |
| CUPTI cost about 0.13 us/launch, scan 33 ns; `LD_PRELOAD` about 30 ns | WEAK | Over 3 runs each: baseline 1.69 to 1.78 us, `LD_PRELOAD` 1.78 to 1.90, CUPTI without scan 1.87 to 2.05, CUPTI with scan 1.87 to 1.96 (scan 31 to 34 ns). The spread between runs (±0.1 to 0.2 us) is as large as the claimed difference, and in one run scan was faster than no-scan. Measured only on a zero-parameter kernel, so the scan cost for real kernels (sgemm has many parameters) is not measured. My scratch test shows the empty-launch loop is mostly CPU-bound: 200 ns of added CPU delay adds about 0.33 us/launch, but 100 ns adds only 0.06, so overheads under about 100 ns are partly hidden. |
| "CUPTI sees everything that reaches the driver" | WEAK | It subscribes only to `cuLaunchKernel(Ex)(_ptsz)`. It misses `cuLaunchCooperativeKernel`, `cuGraphLaunch` and host functions. It tracks allocations from `cuMemAlloc_v2`, `cuMemAllocAsync` and `cuMemMap` only, so pool allocations, managed, pitch and host allocations are missed, and so are `cuMemFreeAsync` and `cuMemRelease`. |
| Kernel time vs. demoted fraction is roughly linear | CONFIRMED | Streaming: 6.49, 16.1, 26.5, 37.2, 52.6 ms at 0/4/8/12/16 chunks. The reported 16/16 values (48.0 and 543 ms) did not reproduce: I got 52.6 and 433 ms, a ±10 to 20% spread between runs. |
| Touched once costs 7x on host, touched 8 times costs 10x, so reuse is the signal for promotion | WRONG | My ratios are 8.1x (52.6/6.49) and 8.3x (433/52.0), effectively equal. `reuse_rw` makes 8 full streaming passes over 512 MiB, more than 20x the 24 MB L2, so the data is never reused from cache: it is the same access pattern done 8 times. The code comment "cache-unfriendly stride" is also inaccurate, because the stride is 1. The experiment shows that cost grows with the number of touches, which is trivially true, and says nothing about reuse. |
| Hashing: 188 GB/s, exactly blocks 137 and 400 flagged | CONFIRMED | 187.9 GB/s; blocks 137 and 400; D2H copy 81.8 ms (13.1 GB/s). The mix function (multiply by an odd constant, then xor-shift) is a bijection, so any single-word change always changes the sum. Only uniform data (`0x5a`) was tested, on `cudaMalloc` memory, not VMM. |
| Access counters only inside `nvidia-uvm`; file:line references | CONFIRMED | `uvm_gpu.c:1435`, `uvm_hal.c:913-914` and `uvm_gpu_access_counters.c:146-157` match the 580.178.04 tree. `/sys/module/nvidia_uvm/parameters/uvm_perf_access_counter_migration_enable` reads `-1`. Non-managed addresses go to HMM, ATS or `notify_tools` (`:1538-1600`). One nuance: the tools access-counter events are test-only (`UvmEventTypeTestAccessCounter`) and sit behind `uvm_enable_builtin_tests=1` (`uvm_test.c:245`), which needs root and a module reload. That strengthens "not usable from userspace". |
| CUPTI has no per-access addresses for non-UVM memory | CONFIRMED | In `cupti_activity.h`, `address` fields appear only on memory, pool and UVM records. |
| NVBit is the only offline ground-truth option | WEAK (missing option) | The Compute Sanitizer API is already installed (`/usr/local/cuda/compute-sanitizer/include/sanitizer_patching.h:222,781`). `SANITIZER_INSTRUCTION_GLOBAL_MEMORY_ACCESS` gives a callback with the address of each access, with no extra install. |

## Methodology issues and suggested fixes

1. Nearly every result is a single run. Repeat each timing at least 5 times and report the median and range, especially the launch-overhead numbers and the `frac` table, where the run-to-run spread equals the claimed effects.
2. The concurrency tests lacked a capacity control. Add the "same total blocks in one process" run (8 blocks: 444 ms) to show that the doubling comes from time slicing.
3. The fault tests did not record when A's fault happened relative to B's kernel. Print the host time in `mode_fault` or around it, as I did, so the overlap is shown rather than assumed. The MPS case shows overlap implicitly through B's failure; the no-MPS "B survives" case needs it shown.
4. Some [run] claims have no code or no command: `cuMemMap` over a mapped range, the two-process remap numbers, `hold`, and the "zero launches with only `cudaLaunchKernel`" run. Add them to `spatial.cu` and the READMEs, or retag them.
5. Pain-signal reuse: to test reuse, use a working set that fits in L2, or compare a pattern with real temporal locality against streaming of equal byte volume. Also measure with a concurrent tenant: under MPS, a tenant's kernel time depends on what its co-tenants are doing, so it is a confounded pain signal.
6. Overhead: measure with kernels that have realistic parameter counts (around 20 parameters, as in sgemm) and with several launching threads, since both shims take one global lock.
7. The guide quotes should cite the version-specific context. The quoted passage is about MPS static partitioning (CUDA 13.1 or later, guide 13.3), while this machine has 13.0.

## Missing

- Green contexts under MPS as a cross-process SM-partitioning mechanism (measured above). This is the strongest spatial-isolation option on CUDA 13.0 and should be in the 2A Answer and in "What this means for libvmem" item 1.
- Whether MPS's memory limit counts `HOST_NUMA` allocations: still open. It is a one-line test, the `vmm` mode with a 128M limit and only a host handle.
- Whether a fault under MPS also kills idle clients, since the server resets the device context.
- 2B: per-launch "last use finished" tracking was proposed but not prototyped. No CUDA-graph or multithreaded test.
